# ZK-OIDC feasibility spike

**Status:** approved for research only; no product integration.

**Goal:** determine whether a real provider ID token can produce a private,
session-bound affiliation proof locally at acceptable desktop/mobile cost,
without relying on the ZK Email conductor or disclosing the raw token to the
Pirate API.

## Claim profiles

### Google

Prove a valid RS256 ID token with approved `iss` and `aud`, fresh Pirate-bound
`nonce`, extracted `exp`, and public `hd`; the server checks `exp` against its
current time. Keep `sub` private and output only an application-scoped salted
nullifier. This proves membership in the hosted organization domain represented
by `hd`.

### Microsoft

Prove a valid token with approved issuer/audience, fresh nonce, server-checked
expiry, and public `tid`. Keep `oid`/`sub` private and derive an
application-scoped nullifier. Separately map `tid` to the tenant's current Graph
`verifiedDomains`. The resulting claim is tenant membership where the tenant
controls the configured domain; it does not prove a mailbox at that domain.
Mutable email-like claims are never authorization inputs.

## Required security properties

1. Verify JWT signature against the exact session-pinned JWK selected by `kid`.
2. Constrain and expose the approved `iss`, `aud`, `nonce`, affiliation claim,
   token expiry result and JWK hash needed by the verifier.
3. Bind the nonce to `{user, session, audience, purpose, expires_at}` and consume
   it atomically with capability/nullifier insertion.
4. Derive the nullifier from stable subject + issuer + audience + Pirate domain
   separation and a circuit input salt; never expose the raw subject or an
   unsalted digest.
5. Pin circuit source, compiler, manifest, WASM, proving key/chunks,
   verification key and hashes. No mutable runtime artifact fetch.
6. Keep ID tokens, authorization codes, claims and proof witnesses out of URLs,
   logs, telemetry, crash reports and API responses.
7. State the client-delivery boundary honestly. A proof generated by ordinary
   JavaScript served by Pirate does not protect the JWT from maliciously changed
   Pirate JavaScript. Operator-blindness requires a trusted/reproducible client
   or an explicitly weaker honest-frontend assumption.

## Go/no-go

Go only if all are true:

- real Google proof correctness and negative tests pass;
- proof/JWK/session binding is explicit and independently reviewable;
- desktop and mobile artifact/proving costs fit the product budget;
- no raw token crosses into Pirate APIs or observability systems;
- the accepted client-delivery assumption is stated and acceptable; and
- circuit/setup provenance is suitable for an audit before production.

A successful prototype is not production authorization. The candidate upstream
implementation's unaudited status requires an independent security review.

## Initial upstream audit — Z1a

Observed 2026-08-10 from `zkemail/zk-jwt` commit
`3a50a9bb80020a5bf7964881dcf70286e22037ab` (latest commit dated 2025-10-07):

- root/circuit package version is `0.1.0`; the helper workspace manifest is
  `0.0.1`. The repository is MIT, while its README notes Circom/circomlib GPL
  considerations. It explicitly says the project is unaudited and not intended
  for production.
- No WASM, R1CS, proving key, verification key or setup transcript is committed.
  The setup script downloads a Powers-of-Tau file and defaults to the literal
  development entropy `dev` plus a fixed beacon when environment values are
  absent. Those defaults are acceptable only for disposable tests and must
  never produce a trusted deployment key.
- The reusable verifier supplies an RSA/SHA-256 JWT-signature and decoded
  header/payload foundation. The current authentication circuit is not our
  circuit: it extracts the mutable `email` domain, `iat`, `azp`, and a
  command-shaped `nonce`; it does not extract/constrain Google `hd`, `aud`, or
  `exp` as required here.
- Its primary `jwtNullifier` hashes the JWT signature and therefore changes with
  the token. An example instead hashes numeric Google `sub` without application
  domain separation, making it cross-application linkable. Neither satisfies
  this spike's stable salted-nullifier requirement.
- `kid` extraction assumes a fixed 40-character hexadecimal identifier. That may
  fit the included Google fixture shape but is not a provider-general JWK key-ID
  representation and cannot be assumed for Microsoft.
- Field extractors validate a caller-supplied occurrence but comments claiming
  uniqueness are not backed by a count of duplicate JSON keys. Duplicate-key
  ambiguity must be a negative test and the custom claim circuit must constrain
  the chosen parsing semantics.
- The real-Google circuit test is skipped and expects a private local fixture.
  Existing green synthetic tests do not establish a current provider flow.
- Do not reuse or deploy the included demo frontend/API. It sends the JWT to a
  server input-generation endpoint and a remote prover, logs circuit inputs and
  proof material, logs decoded JWT data in the browser, and sends identity/proof
  fields to analytics. Those behaviors directly violate this spike's privacy
  requirements.

**Z1a verdict:** the repository is useful RSA/base64/Circom research material,
not a drop-in private OIDC implementation. Z2 requires a small purpose-built
claim circuit and local-only harness derived from reviewed primitives. This is
more work than the initial “prove an existing token” framing implied, but still
materially smaller in input/parsing scope than the email circuit. Proving cost
and artifact size remain entirely unmeasured.
